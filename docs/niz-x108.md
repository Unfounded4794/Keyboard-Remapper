# NIZ x108 native adapter — version 0.7.1

Validated device: `0483:5230`, HID collection usage page `0x008C`, usage `1`, input/output report ID `0`, 64-byte payload. It identifies as `Program`; the firmware reply is `X108EC(S);V1.0.22;V1.0;`. Recognition requires both the interface descriptor and this firmware identity. Other x108/XRGB/Bluetooth firmware revisions are not inferred from the name. The normal keyboard/system-control interfaces are never opened for configuration.

The adapter is automatic and uses the existing USB connection, keymap, macro and tester views. No firmware flashing, calibration, reset, keyboard lock or OS driver replacement is performed. It does not install or launch the manufacturer's Windows software. Host-event testing remains available; this protocol adapter does not claim VIA physical matrix monitoring or live USB polling capture.

## Protocol and preservation

Payloads begin `00 <command>`. `F9` reads the version. `F2` streams `00 F0 layer key type ...` records until a report beginning `F6`. This board supplies 216 records: 108 physical keys × 2 layers. Physical key IDs are distinct from NIZ internal action codes; keypad zero/decimal/Enter use physical IDs 106/107/108. The built-in geometry uses fixed physical identities rather than inferring key positions from user-remapped output codes.

Type 0 is a normal key/chord; type 1 is repeat; types 2–4 are sequence playback modes with 53 payload bytes per continuation. Existing records are retained byte-for-byte. Standard keys/media/modifiers translate between NIZ internal actions and the app's shared keycodes. Native Fn, mode, lighting and other firmware functions retain their NIZ codes; unsupported QMK actions are excluded from the palette and rejected before writing. Non-simple records use a per-key reference, not fictitious shared VIA macro slots. Macro references cannot be transferred to a different key through a custom numeric keycode.

The graphical macro editor handles balanced key transitions and once-only playback (type 2, cycles 1), including recorded/fixed/per-event delays. Repeated internal key codes toggle press/release; delay marker 200 carries a big-endian 16-bit interval. Sequence continuations retain their 11-byte headers. Chords are represented as press/release pairs; unsupported playback modes and unbalanced existing sequences are shown as opaque raw expressions. Those expressions cannot accidentally be recompiled into different actions; replace them deliberately to create a new sequence. Leading/trailing delays and text literals are rejected rather than silently altered.

Version 0.7.1 fixes zero-delay playback. The recovered firmware's [macro player at 0x82F4](https://github.com/cbingb666/niz-firmware/blob/main/recovered/firmware/decompiled/functions/000082f4_FUN_000082f4.c) continues its inner custom-delay loop on a zero interval, before flushing the USB keyboard report. A press and release can therefore cancel out before the host sees either, even though the saved record verifies byte-for-byte. Uniform timings now use fixed-interval mode; mixed timings use positive custom gaps. New sequences use at least 3 ms per transition, matching the wired fixed-mode floor in [key event dispatch](https://github.com/cbingb666/niz-firmware/blob/main/recovered/firmware/decompiled/functions/00004ab4_key_events_dispatch.c). Existing records remain unchanged until resaved. A narrow independent playback model reproduces the previous empty-host-report failure and checks visible Ctrl+V transitions, including the Fn Left Shift target (wire group 2, physical key 55). The GUI regression records and saves this exact no-delay case. The owner confirmed that Ctrl+V pastes correctly on the physical x108 in 0.7.1 on October 14, 2026. Ordinary remapping was also reported working. Persistence across reconnect/power cycle has not been separately confirmed.

The existing layer buttons now read **Base** and **Fn** for NIZ, with a tooltip identifying Right Fn as the physical modifier. Selecting an editing layer in the app does not activate that layer on the keyboard.

Applying key changes stages all edits first. Before sending `F1` (begin full-profile write), the adapter re-reads and compares the complete live configuration, validates all desired records and saves the original raw reports in localStorage `keystone.niz-recovery`. It sends every record with 3 ms pacing, then `00 F6 F6 ...`, waits 300 ms and compares the entire readback. Other macros and layers remain byte-preserved. Macro saves follow the same path, and pending keymap drafts must first be applied or cancelled. Interrupted/stalled transfers require reconnecting. This is not an atomic firmware transaction; the recovery copy preserves the pre-write data but automatic rollback after a partial write is not attempted.

The layout JSON export remains a keymap backup, not a full NIZ macro archive. The raw recovery copy is separate. Programmable mappings run in the keyboard's M/program mode; Office mode uses its fixed functions.

## Validation (October 14, 2026)

Real x108 read-only checks: version query, 216 configuration records, 108-key keymap, two layers, native Fn/media labels, per-key macro dropdown and graphical decoding of its existing sequence. Screenshot: `artifacts/niz-x108-keymap-v7.png`. No mappings or macros were changed on the real keyboard. Numpad geometry was visually reviewed against the live record numbering.

Simulated tests cover complete-record validation, continuation framing, balanced macro encoding and delay boundaries, preservation of unknown playback records, full-profile backup/write/readback, stale baseline refusal, readback failure and rejection of unqualified firmware. GUI tests exercise automatic connection and saving through the existing graphical macro controls. Physical write persistence and macOS/Linux hardware access still require qualification.
